- 默认面向单台工作站设计——无需任何额外配置、不依赖外部服务。此外还提供一种可选启用、通过环境变量激活的分布式模式（见[《10.
  分布式部署》](10_distributed_deployment.zh-CN.md)）：当一批导入任务的文件足够多，把解析工作分摊到多台机器上确实能节省总耗时；当
  Sigma 规则集足够大，逐条规则在单机上求值本身成了瓶颈；或者多名分析师希望在不各自保留本地完整拷贝的前提下，同时查询同一个共享案例时，分布式模式会有帮助。但它**不会**加速单条查询或单个较小的案例——无论是否启用分布式模式，查询执行本身始终是单机
  DuckDB 完成的，具体边界见该指南。在此前提下，不同日志类别的现实规模差异很大：EVTX
  案例通常远低于 100GB，而一个案例范围内的 Web 访问/错误日志现实中可以达到 TB 级别。
- 导入并行度（`--workers`）本地默认最多使用 8 个进程。文件虽然相互独立，但解析进程内存与并发读取证据磁盘会让不受限的“CPU 核心数并发”在许多工作站上适得其反。高速 NVMe 或内存更紧张的机器可显式调整 `--workers`；分布式模式仍会把任务分发到可用的 `seclogx worker` 进程。
- 来源目录树现在只会被遍历**一次**，而不是两次。修复之前，`ingest`
  会先用一次单线程遍历发现 `.evtx` 文件，然后再用*第二次*、独立的单线程遍历去发现并按内容对其余所有文件分类——对于一个真实的证据集（成千上万个体积不大、类型混杂的文件，其中一部分根本不是受支持的日志类型）而言，第二次遍历本身——一个
  Python 循环、单线程、每个候选文件一次 16KB 读取加上一连串正则匹配（`sniff.classify_file`）——才是实际的主要耗时来源，而不是单文件解析吞吐量本身，并且整个过程没有任何输出。`ingest.scan.scan_sources()`
  现在对每个 `--source` 根目录只遍历一次，并用线程池并行对非 `.evtx`
  候选文件做内容分类（这个内容抽样是 I/O 密集型的，用线程即可获得加速，不像
  CPU 密集型的解析工作那样需要独立进程）。`.evtx` 通路与非 `.evtx`
  通路随后会**并发**执行，而不是先后执行，各自仍维护自己有上限的工作进程池——当两者都有工作要做、且未显式指定
  `--workers` 时，默认的工作进程预算会在两者之间**均分**而不是翻倍，因此并发执行时的峰值工作进程数（以及峰值内存）不会比一次只跑一条通路时更高。
- 这次唯一的遍历改用 `os.scandir`，而不再是 `Path.rglob("*")` 加上对每个条目的
  `is_file()`、`resolve()` 与 `stat()`。后者对每个文件要付出三到四次系统调用（外加
  `resolve()` 对路径每一段做的 readlink 解析），而 scandir 直接从读目录的结果里就能拿到条目类型，只需要一次
  stat：在一个 24000 个文件的取证目录树上（缓存已预热）**实测快 4.6
  倍**，而在冷缓存、网络挂载或机械硬盘上，由于系统调用次数占主导，差距会更大。跨
  `--source` 的去重现在以那次 stat 得到的 `(st_dev, st_ino)`
  为键，而不再是解析后的路径——这不额外增加任何开销，还能顺带识别硬链接。符号链接的处理行为保持不变：指向日志文件的符号链接仍会被跟随并导入，而符号链接*目录*不会被递归进入（因此符号链接成环也不会让遍历卡死）。遍历过程中还会持续汇报已发现的文件数，所以大批量导入的第一个阶段不再是完全没有输出的。
- 暂存解析结果时，写 NDJSON 复用**同一个 `json.JSONEncoder`**。只要传了任何非默认关键字参数，`json.dumps(row, ...)`
  就会每次调用都新建一个编码器、绕过模块内缓存的那个；在一次 60 万行导入的性能剖析中，这一项排进了开销前三。再加上手写的
  Common Log Format 时间戳解析（`ingest/logsources/parsers/webaccess.py`）——对固定宽度的常见格式直接切片取值，而不调用
  `datetime.strptime`，单次调用**快 4.5 倍**，而这个调用每条访问日志行都要发生一次，同时仍保留
  `strptime` 作为少见但合法变体的兜底——两者合计使**单文件暂存的 CPU 开销下降约 22%**。
- `ingest` 在前台模式下会展示一个**实时进度显示**（当前阶段、目前已扫描的文件数、已暂存的成功/部分/失败/不支持计数、各表已写入的行数），而不是在整个运行期间毫无输出。`--background`/`-b`
  会将导入过程放到独立的后台进程中执行并立即返回，同时打印出用于查看进度的确切命令
  `seclogx ingest-status <case> --watch`——适合分析师不想在终端前干等的大批量导入场景。状态保存在一份小体积的
  JSON 快照 `cases/<name>/jobs/<job_id>.json` 中，运行过程中会（经过节流，而非每个文件都写一次）持续更新，并以原子方式写入，因此并发的
  `ingest-status` 读取绝不会看到写了一半的文件；后台任务被捕获的标准输出/标准错误会写入同名的
  `.log` 文件。见[《5. 命令行参考》](05_cli_reference.zh-CN.md)。
- 把暂存的 NDJSON 展平（flatten）为 Parquet 时，现在只对数据扫描**一遍**，而不是两遍。DuckDB
  的 `COPY ... PARTITION_BY` 本身就会创建 Hive
  分区目录，但两个并发写入方同时创建同一个新目录时在 Windows
  上会发生竞争，因此原先每次 COPY 之前都会先枚举一遍分区取值（`SELECT
  DISTINCT`，也就是把每个暂存文件完整重读并重新解析一次
  JSON），再预先创建这些目录。实测这一步占**展平耗时的约
  32%**，却是在所有平台上都付出代价、只为解决一个 Windows
  独有的竞争问题；现在它由 `StorageBackend.precreates_partition_dirs`
  控制，仅在 Windows 上的本地存储后端为真。POSIX 上的 mkdir
  竞争本身是无害的，而对象存储根本没有目录的概念。
- `.auth_events()` 现在会先在 **SQL 层**把 `syslog`
  收窄到具备登录/认证特征的行（见
  `AUTH_EVENT_CANDIDATE_SQL`），再交给 pandas，而不是把整张表都materialize
  出来逐行过滤。syslog 正是现实中可能达到数百万乃至更多行的日志类别之一，而其中
  SSH/sudo/PAM/账户管理相关的行只占一小部分，因此原先的写法恰恰会在这个视图最有用的场景下有耗尽内存的风险。这个
  SQL 过滤条件被刻意设计成启发式规则所接受集合的**严格超集**，因此结果完全一致——并有一个测试将其与“对全表跑同一套启发式规则”的结果做逐行比对来保证这一点。
- 查询与狩猎都直接通过 DuckDB 针对按 Hive 方式分区的 Parquet 数据湖执行，具备惰性、核外（out-of-core）执行能力与谓词下推：一个限定了主机/通道/时间范围的查询，只会读取实际需要的
  Parquet 行组，而不会把整个数据湖都载入内存。不过，*取回*一个未加过滤的大结果时，默认仍然是单个
  DataFrame（`.query()`/`.table()`/`.web_logs()` 等，底层调用 DuckDB 的
  `fetchdf()`）——对于尚未过滤/聚合到较小规模的表或查询，请改用 `_chunks`
  同名方法（`.query_chunks()`、`.web_logs_chunks()`、`.timeline_chunks()` 等），其内存占用由
  `chunksize` 决定，而非结果总量。完整说明与示例见[《3. 查询与搜索》](03_querying_and_search.zh-CN.md)中的“大表的有界内存访问”；命令行（`query`/`table`/`tasks`/`timeline`）在
  `--out` 导出和控制台预览时都会自动使用这一机制，无需任何额外参数即可获得有界内存的行为。
- `.search()` 会在取回结果之前先估算其规模（精确的 `count(*)`，乘以从一个
  `LIMIT` 有界样本得出的单行字节数，再外推到全部行数——两步的开销都与表的总大小无关，因此这个估算过程本身不会耗尽它原本想要保护的内存），并与机器当前实际可用内存的四分之一做比较，超出就拒绝取回而不是硬取。可用内存的检测是尽力而为的（Linux
  上读 `/proc/meminfo`，其他平台用更粗略的兜底方式），如果完全无法确定，则回退为固定假设
  200MB 可用，而不是假设机器内存无限。见[《3. 查询与搜索》](03_querying_and_search.zh-CN.md)中的“内存安全检查”。
- `--keep-raw` 会使被应用文件的导入耗时与峰值内存大致翻倍——建议只在需要完整 XML
  保真度的特定证据上选择性使用，而不要对整个大型案例默认开启。
- 计划任务/IIS/Web 访问/Exchange/syslog/auditd/journal/数据库/腾讯云/注册表日志现在也和 EVTX
  一样，先按文件暂存为 NDJSON，再由 DuckDB 直接从磁盘读取（`read_ndjson_auto`）后写入
  Parquet，而不再是把某张表在整个批次范围内的所有已解析行都累积在 Python 内存中。导入时的峰值内存现在由
  “单个文件的解析开销 × `workers` 数”决定，而不再由整个批次的总大小决定——即便一个批次的文件多到总量达到
  TB 级别，导入过程也不需要把它们一次性放进内存。腾讯云客户端日志只保留一条前视记录并直接流式写入 gzip 暂存，因此内存与文件大小无关，同时仍能正确合并多行记录。其他部分非 EVTX 格式仍会一次性读取单个文件，所以这些类别中的异常巨大文件仍然是按文件计算的内存开销，而不是按批次。
- 暂存的 NDJSON（`staging/`、`staging_aux/`）会以 gzip 压缩（压缩级别 1）而非纯文本方式写入，且默认保留（见[《5.
  命令行参考》](05_cli_reference.zh-CN.md)中的 `--keep-staging`），以便案例可以在不重新解析证据的前提下低成本地重新展平（flatten）。渲染为
  JSON 的 EVTX 记录尤其会比原始二进制 `.evtx` 大出不少——未压缩且默认保留的组合，正是案例目录体积膨胀到源证据体积数倍（而非一个零头）的主要原因；gzip
  能把暂存目录的体积压回接近（通常小于）源文件大小，压缩本身的开销相对于同一个
  worker 中已经在做的解析工作来说很小，DuckDB 的 `read_ndjson`/`read_ndjson_auto`
  会透明地读取并解压，不会带来明显的额外读取开销。如果磁盘比时间更紧张，可以用
  `--no-keep-staging`：一旦展平成功就彻底删除暂存目录——代价是失去低成本的重新处理能力（之后如果需要修复 schema
  或重新展平失败的批次，就得重新导入源文件，而不能只重跑展平步骤）。
- 证据目录中混入的非日志内容（PE/ELF 二进制文件、内存转储等）的排除成本很低：已知的二进制扩展名（`.exe`/`.dll`/`.sys`
  等）在读取任何内容之前就按扩展名跳过；其余文件只会做一次 16KB 的内容抽样（`sniff.classify_file`）来判断是否属于受支持的格式——分类阶段从不整文件读取。一个不匹配任何受支持格式的文件（会记录在
  `AuxIngestReport.unknown_samples` 中，绝不会被静默丢弃）也不会被计算哈希或暂存，因为这两者都是为了给已写入某张表的数据提供溯源，一个没有归属表的文件用不上；只有真正匹配某个受支持格式的文件，才需要付出整文件读取来计算哈希的开销。未知文件还会直接在协调进程生成报告，不再为每个文件创建本地进程池/分布式任务；当软件采集目录里有数千个程序文件而只有少量日志时，这能显著减少调度开销。
